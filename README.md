# AI Seller Agent

API для сопоставления пользовательских сообщений с товарами из CSV-каталога.

## Требования

- Python 3.12 или новее
- `uv` для разработки и сборки

Каталог является внешним файлом и не включается в Python-пакет. По умолчанию
приложение читает `data/catalog_excel.csv` относительно корня репозитория.

## Локальный запуск

1. Клонировать репоизторий:
```bash
git clone git@github.com:mrKazzila/ai-seller-agent.git
```

2. Перейти в директорию с репозиторием:
```bash
cd ai-seller-agent
```

3. Установите зависимости и создайте локальный файл настроек:

```bash
uv sync
cp env/.env.example env/.env
```

4. Запустите приложение из корня репозитория:

```bash
uv run agent
```


## Экспорт зависимостей для pip

Production-зависимости:

```bash
uv export --locked --format requirements.txt --no-dev --no-emit-project --output-file requirements.txt
```

Production и dev-зависимости:

```bash
uv export --locked --format requirements.txt --no-emit-project --output-file requirements-dev.txt
```

Оба файла являются производными от `uv.lock`, после изменения зависимостей их
следует создать заново этими же командами.

## Сборка и запуск без uv

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install ./ai_seller_agent-0.0.1-py3-none-any.whl
.venv/bin/agent
```

При установке wheel `pip` установит зависимости из metadata пакета. Если нужно
установить зафиксированные версии заранее, используйте:

```bash
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip install --no-deps /path/to/ai_seller_agent-0.0.1-py3-none-any.whl
```


## Принятые решения

Для сопоставления сообщения с каталогом используется комбинация TF-IDF,
покрытия токенов запроса, RapidFuzz и проверки характеристик товара.

TF-IDF из `scikit-learn` используется для
основного поиска похожих названий (символьное представление устойчивее к
опечаткам, окончаниям и неполным словам, чем сравнение только по словам).

`RapidFuzz` дополнительно оценивает нечёткое сходство всего запроса с названием товара.
Из текста также извлекаются размеры, резьба, зернистость, типы бит и
коды моделей, количество в упаковке, напряжение, число зубьев и маркировки.
Покрытие токенов запроса помогает не занижать оценку короткого точного запроса
относительно полного названия товара.

Итоговая оценка объединяет три результата. Пороги оценки и отрыв первого
кандидата от второго определяют статус `matched`, `ambiguous` или `not_found`.
В сомнительном случае система возвращает `ambiguous`.

Решение работает локально и не требует внешних сервисов, но зависит от ручных
правил нормализации и настройки весов.

Каталог загружается из CSV при старте и хранится в памяти вместе с поисковым индексом.
Изменения файла не подхватываются без перезапуска.

Код разделён на domain, application, infrastructure, presentation и
entrypoints. Application-сценарии зависят от портов, а работа с CSV, каталогом
в памяти и поиском вынесена в infrastructure. Доменная политика отдельно
принимает решение о статусе и не зависит от FastAPI.

Зависимости явно собираются в bootstrap. В `app.state` сохраняются готовые use case, доступные через зависимости
FastAPI.

Для зависимостей используется `uv`, для линтинга и форматирования `ruff`,
для проверки типов `ty`, для тестов `pytest`.
Тесты разделены на unit, integration и e2e, включают параметризацию и негативные сценарии.
Логирование реализовано через структурированные логи `structlog`.

## Рассмотренные альтернативы и ограничения

Облачная LLM не использовалась, поскольку ТЗ требует автономной работы без интернета, внешних API и ключей.

Локальную embedding-модель вроде `all-MiniLM-L6-v2` не использовал, поскольку
для 500 товаров она добавляет тяжёлую зависимость и отдельный индекс без
подтверждённой пользы. Для русского каталога также потребовалась бы подходящая
русскоязычная или мультиязычная модель.

Полноценное сравнение текущего алгоритма с embeddings или локальной LLM не
pроводил. Нагрузочное тестирование также не выполнялось.


## Что необходимо до production

- Добавить метрики (latency, ошибок, размера каталога и распределения статусов) в идеале tracing и алерты.
- Добавить CI/CD, pre-commit, Dockerfile и окружение для локального запуска.
- Ограничить размер batch, добавить timeout, rate limiting.
- Кешировать результат по магазину, запросу и версии каталога.
- Подготовить независимый размеченный набор и измерять precision, recall@K и доли
  `matched`, `ambiguous`, `not_found` после изменения правил и весов.
- Реализовать безопасное обновление и версионирование каталога.


## Масштаб: 2 миллиона товаров и 50 магазинов

PostgreSQL должен стать источником истины, а API быть stateless. В данных нужно
разделить `tenant_id` компании, `store_id` магазина и версию каталога. Каждый
запрос должен быть ограничен текущим магазином. Для точного поиска SKU нужен
уникальный B-tree индекс по `(store_id, sku)`.

Для поиска следует хранить нормализованное поле `search_text`, подключить
`pg_trgm` и добавить GIN trigram-индекса.
PostgreSQL будет выбирать небольшой список кандидатов, а RapidFuzz и проверка характеристик, ранжировать только
этот список. `scikit-learn` после этого можно убрать из online-пути.

Я бы оставался на PostgreSQL, пока он выполняет требования по времени ответа и
нагрузке. При высоком QPS или сложных поисковых сценариях можно рассмотреть
Elasticsearch и обновлять его индекс через CDC или outbox.
